| D-20 | ICMP pinger | Decided (partly implemented) | Our own `pinger` worker: asyncio ICMP with `icmplib`, respects `polling_owner`. **Amended from the original proposal after implementing it:** unprivileged ICMP (Linux datagram sockets, `privileged=False`) needs no capability at all, so `CAP_NET_RAW` is not granted by default - only if a hardened kernel's `ping_group_range` disallows the unprivileged path. The new pinger reproduces exactly that: it exposes a gauge literally named `pinger_host_status` (a deliberate, documented exception to D-26's `cybersathy_` metric prefix, since renaming it would mean editing a rule otherwise kept byte-for-byte) and decides no alarm itself | 12, 20, 24, 26 |

| D-28 | Service-only permissions | Decided (implemented) | A permission that has no interactive owner (its only caller is another service, not a person) is never granted to any role. `api_tokens.manage` alone is not enough to use such a permission from a session — it only lets its holder *mint a token* scoped to it, via a narrow, explicit `SERVICE_ONLY_PERMISSIONS` allow-list checked both at token creation and at authentication time. First use: `events.ingest`, held by no role, so a leaked interactive session can never call the Alertmanager webhook, only a token created for it can | 20, 36 |
| D-29 | The legacy "trusted network" list | Proposed | **Not ported as an authentication path.** Legacy `TRUSTED_HOST_NETWORK_LIST` and `LOCAL_SUBNET` authenticate a request by its source address alone, and from a trusted address `?USER_ID=` selects any user to act as (R-08). The new system authenticates every request by a credential: a session, or an API token for services (D-04, D-28). Each legacy caller that relied on the list gets its own scoped API token. **Open question for the owner:** should the new system also have a global network *restriction* (sessions and tokens accepted only from listed networks, on top of the credential)? It would narrow access, never widen it, but a wrong list locks everyone out, so it waits for an answer | 36, 39, 41 |
| D-30 | Reading a column the MIB marks writable | Proposed | **Not allowed today; the profiles go without.** The registry refuses to poll any object whose MIB access is not read-only (Plan 6), and that rule is kept. It costs two things in Plan 18: RMON rows cannot be tied to interfaces, because `etherStatsDataSource` is read-write, so `rmon_errors` keys rows by `etherStatsIndex` only; and the VLAN summary has no names, because `dot1qVlanStaticName` is read-create. Plan 19 adds two more: RFC 1213's ARP table (`ipNetToMediaTable`) and route table (`ipRouteTable`) are read-write too, so router ARP comes from the RouterOS API and SNMP-only L3 routers have no ARP view until this is decided. **Open question for the owner:** allow a GET-only use of named writable columns (each listed by name, still never SET)? It would complete these profiles, but it weakens a rule that is currently absolute, so it waits for an answer. Until then a per-vendor fixture showing `etherStatsIndex` equals ifIndex is the other way to map RMON rows | 6, 18, 19 |

## Rules for changing a decision

- A decision that touches security, scope or device safety is reviewed by whoever owns access control before it moves to `Decided`.
- If a decision changes, update every plan listed in **Affects** in the same change.
