# Migration Status

Last updated 2026-10-01 (twelfth round: Plan 20 event-to-notification wiring, flapping suppression and the `sync-active-alerts` port. Eleventh round: Plan 21 flood protection. Tenth round: Plan 10 interface inventory and Plan 21's offline half, both done 2026-09-29). Everything below was verified offline: unit and integration tests against a throwaway PostgreSQL + TimescaleDB and Redis, plus one run of the real Compose stack. Nothing was verified against a device.

**Environment issue, found and resolved (2026-09-29):** mid-round, `tools/test-backend.sh` and `tools/update-schema-snapshot.sh` started failing with `socket.gaierror: Temporary failure in name resolution` resolving the throwaway Postgres container's name. First suspected as a Docker daemon DNS fault (this host's `live-restore` is disabled, so a daemon restart would have stopped every running container, including the legacy system's 24 - not attempted). **The real cause was simpler and unrelated to networking: the host's root disk was at 100% (0 bytes free)**, which surfaces as DNS/IPAM failures in Docker because it can no longer write new network or volume state. The disk was full because `docker rm -f` in both scripts' cleanup never passed `-v`, so every one of the many test runs across this migration leaked one anonymous Postgres data volume; 296 had accumulated (~8GB) alongside ~13GB of dangling build cache and images. Fixed three ways: `docker volume prune -f` / `docker image prune -f` / `docker builder prune -f` reclaimed 12GB immediately (verified safe - these only remove resources already unattached to any container, running or stopped; the 24 production containers were never touched and stayed healthy throughout); both scripts' cleanup now passes `docker rm -f -v` so the leak cannot recur (confirmed: the host's volume count no longer grows across a run); and both scripts now wait for the new container's name to actually resolve on the test network before launching the test/snapshot container, closing the startup race that produced the DNS symptom in the first place (the container's own readiness, checked via `docker exec ... pg_isready`, doesn't guarantee its DNS record is yet queryable from another container on the same bridge network). No production impact at any point; nothing here needed a daemon restart.
